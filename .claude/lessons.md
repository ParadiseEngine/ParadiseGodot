# Project Lessons — ParadiseGodotEditor

## Runtime / Architecture

- [hits: 1] **Coordinate contract is now RIGHT-HANDED (Y-up, −Z forward, column-major), everywhere** — export data, the shared runtime simulation, and the engine. Flipped from the old Unity-left-handed pin (2026-07-01). `ParadiseExport/Geometry/CoordinateConversion.cs` was **deleted**; the exporter (`SceneDataExporter`, `PrefabExporter`, `NavMeshBake`) writes Godot values verbatim (no Z-mirror, no navmesh winding reversal). The golden fixture `Fixtures/SampleScene.expected.json` is the Unity baseline with its Z-dependent values mirrored to RH. `ParadiseEngine` had NO handedness-baked code and no contract loader, so its part was doc-only (`CLAUDE.md` coordinate section). Don't reintroduce a handedness conversion anywhere.

- [hits: 1] **Shared engine-agnostic simulation lives in `ParadiseGame` (+ `ParadiseGame.Navigation.Detour`)** — the BankHeist (`~/proj/bank-heist`) pattern: one engine-agnostic Core (Paradise.ECS components + `NavMeshFollowSystem` + `INavigationMesh` seam + `NavigationPlanner`) consumed by BOTH the Godot presentation and (future) the ParadiseEngine runtime. Godot is a thin bridge (`runtime/EcsSceneBridge.cs`, NOT `#if TOOLS`): scene-node → ECS entity, input, tick, transform write-back. DotRecast (`DetourNavigationMesh`) is the single shared nav backend for both hosts. **Presentation accesses the ECS world DIRECTLY** — raw `Entity` handles, `GameSimulation.World.CreateEntity(...)`, `.GetComponent<LocalTransform>(e)`, `NavigationPlanner.PlanMoveTo(sim.World, ...)`. No `EntityRef`/facade wrapper (do NOT reintroduce one — the user wants direct ECS access, BankHeist-style). `GameSimulation` exists ONLY to own the world+schedule lifetime (their source-generated generic types can't be named in a caller's field) and exposes `public World World`; Paradise.ECS's `TaggedWorld`/`SharedWorldFactory`/`EntityBuilder`/`GetComponent` are all public and usable cross-assembly.

- [hits: 1] **Paradise.ECS runtime API** (from `Paradise.ECS.Sample`): `[DefaultConfig] IConfig` → generator emits `SharedWorldFactory.Create()`/`World`/`SharedWorld`; `[Component] partial struct` (unmanaged — a C# 12 `[InlineArray]` field for a waypoint buffer works fine); `[Tag] partial struct` (needs `Paradise.ECS.Tag` ref); `world.CreateEntity(EntityBuilder.Create().Add(..).AddTag(default(T)))`, `world.GetComponent<T>(e)` returns assignable `ref`; systems are `ref partial struct : IEntitySystem` with injected `ref`/`ref readonly` component fields; `SystemSchedule.Create(world).Add<S>().Build<SequentialWaveScheduler>().Run()`. To store a schedule without naming its generated generic type, capture `schedule.Run` as an `Action` and hold the schedule as `IDisposable`. Reference `Paradise.ECS.Generators` as `OutputItemType="Analyzer" ReferenceOutputAssembly="false"`. **Systems inject only a fixed set of field kinds** (component `ref`/`ref readonly`, `Span<Component>`, queryable Data/ChunkData, `EntityCommandBuffer`, `Entity`) — there is NO arbitrary-instance injection and NO singleton/resource store. So shared per-frame data (delta time, input) must be modelled as a **component** carried by the entities a system processes and injected as a `ref readonly` field. Refresh it once per tick before `Run()` by iterating a `[Queryable][With<TheComponent>]` and writing each `data.TheComponent` (see `SimulationContext` + `GameSimulation.Tick`). Do NOT use a `static` for frame data (global mutable state — the user rejected it).

- [hits: 1] **Runtime entity identity: use the `paradise_entity_guid` node metadata + node groups, NOT the `EntityExport` script** — `EntityExport` is `#if TOOLS`, so it (and its `IsAgent`/`MoveSpeed` exports) is absent at play time. Node metadata and group membership survive to runtime. The bridge reads `HasMeta("paradise_entity_guid")` for entities and `IsInGroup("paradise_player")` for the player; agent tuning comes from bridge `[Export]` defaults.

- [hits: 1] **Runtime navmesh: load the exported `.bin` (`data/scenes/<Scene>.navmesh.bin`, DotRecast MeshSet) via `DetourNavMeshLoader.LoadFromBytes/LoadFromFile` — NOT from Godot's `NavigationRegion3D`.** This keeps the runtime nav Godot-independent: both the Godot bridge and the engine runtime load the identical file. The exporter (`NavMeshBake` + `NavMeshBinaryWriter`) bakes the carved walkable surface at authoring time; the runtime just reads it (`DtMeshSetReader().Read(reader, maxVertsPerPoly: 6)`). Caveat: the `.bin` must be current — it regenerates on in-editor scene save; the on-disk `sample.navmesh.bin` is stale-LH until re-saved after the RH flip. Note `NavMeshBinaryWriter.BuildNavMesh` (used by the in-memory `DetourNavigationMesh(verts,indices)` test ctor) does NOT carve obstacles — it treats input triangles as the walkable surface as-is; that's why runtime uses the pre-baked `.bin`, not raw scene geometry.

## Navigation (DotRecast)

- [hits: 2] **The navmesh bake's `AgentRadius` must match the agent's body radius (sample capsule = 0.4) — never 0.** Path following steers the agent's CENTER along planned corners; with `AgentRadius = 0` the walkable surface (and therefore planned paths) runs flush against obstacle faces, so the capsule grinds/sinks along walls. Recast erodes by the radius at bake time; keep `NavMeshBake.cs`, the scene's `nav_preview` NavigationMesh, and the capsule radius in sync. Since movement collision moved to Paradise.Physics (2026-07-02), the erosion's job is PATH CLEARANCE (corners keep ≥ radius from faces) — guarded by the repurposed `BakedNavMeshClearanceTests`; the old WASD `MoveAlongSurface` clamp is gone.

- [hits: 1] **DotRecast navmesh triangles must have +Y (upward) normals — the "reversed" fan `poly[0], poly[i], poly[i-1]`, NOT the naive `poly[0], poly[i-1], poly[i]`.** Wrong (−Y) winding still *builds* a navmesh and `FindPath` still finds a corridor, so it looks fine — but `FindStraightPath`'s funnel gets left/right portals swapped and returns a **zig-zag** corridor (corners darting side to side). Symptom: agent moves erratically/unpredictably in play. Godot's baked `NavigationMesh` polygons fan to −Y naively, so `NavMeshBake` must reverse the fan. Guard it in tests with a **path-tautness assertion** (total length ≈ straight-line distance on open ground) — a plain "reaches the goal / count ≥ N" test passes even when zig-zagging.
- [hits: 1] **Read our navmesh `.bin` with `DtMeshSetReader.Read(BinaryReader)` — the no-`maxVertsPerPoly` overload.** `NavMeshBinaryWriter` writes the modern DotRecast format (`DtMeshSetWriter.Write(..., cCompatibility: false)`), which stores params (incl. nvp) in the header. The `Read(br, maxVertsPerPoly)` overload is the C++ Recast-demo compatibility path and misreads this format.
- [hits: 1] Keep `DetourNavigationMesh.RepairInternalAdjacency` (ported from bank-heist): the MeshSet serialize→deserialize round-trip can drop interior poly-to-poly `neis`; the repair re-links shared edges. Defensive/idempotent.

## Threaded simulation / snapshots

- [hits: 1] **`World.CopyFrom` is only on the plain `World<TMask,TConfig>` — NOT on `TaggedWorld`.** When `Paradise.ECS.Tag` is referenced and a config has `[DefaultConfig]`, the generated `World` alias resolves to `TaggedWorld<…>`, which has no `CopyFrom` (build error CS1061). The double-buffered snapshot model needs `CopyFrom`, so `ParadiseGame` **dropped the (unused) `PlayerControlled` tag + the `Paradise.ECS.Tag` reference** → `World` becomes the plain type with `CopyFrom` (clears target, copies all entities/components, **preserves Entity handles** — required to match entities across snapshots for interpolation). The `Paradise.ECS.Concurrent` variant is unusable here: no `CopyFrom`, no `SharedWorld`/factory, and the generated systems/tags target the single-threaded `TaggedWorld`.
- [hits: 1] **Paradise.ECS `SharedWorld.CreateWorld()`/`Dispose()` are thread-affinity-guarded (DEBUG-only, `[Conditional("DEBUG")]`) — they throw `Object was accessed from thread N` if called from a thread other than the one that first called them.** `World`'s own ops (`CreateEntity`, `CopyFrom`, `GetComponent`, `IsAlive`, `Query`, `schedule.Run`) are NOT guarded and are fine cross-thread on immutable snapshots. So for a threaded sim: **pre-create the whole world pool on the owner (main) thread in the ctor**; the sim thread only *pops* from the pool (never `CreateWorld`). The Godot Mono editor runs a DEBUG build, so this fires there (headless run: `--headless --path . res://scenes/sample.tscn --quit-after N` at `/Users/quabug/Downloads/Godot_mono.app/Contents/MacOS/Godot` surfaces it). Symptom in play mode: "can't control the PC" — the sim thread faults on the first tick and stops producing snapshots. Since the pool is bounded, a stalled renderer that pins every world makes the sim **skip ticks (backpressure)** rather than crash.

- [hits: 1] **Snapshot lifetime = reference-count, not a fixed ring.** `SimulationRunner` publishes immutable world snapshots on a 60 Hz sim thread; Godot reads the latest two on its render thread and interpolates. A world is returned to the reuse pool only when it's outside the interpolation window **AND** not pinned by the renderer (`TrySampleInterpolation` pins the pair it hands out and releases the previous pair on the next call). This keeps a snapshot alive as long as the renderer is still reading it — correct even if the render thread stalls, unlike a fixed N-deep ring that could recycle a world mid-read. Cross-thread reads are safe because published worlds are immutable, the sim is the single `ChunkManager` writer, and `ChunkArray` blocks never move. Node writes stay on Godot's main thread (`_Process`); interpolate ~2 ticks behind (`renderDelay = 2/60`), skip-ahead past `4/60` lag.

## Stateless physics (Paradise.Physics)

- [hits: 1] **A capsule resting EXACTLY on the floor makes every horizontal capsule cast report a fraction-0 hit against the floor** (surfaces touching = distance 0 ≤ contact epsilon), freezing movement. Two-part fix, both required: character casts use a `CollisionFilter` that excludes the Floor layer (`PhysicsLayers.CharacterCast`, Godot `collision_layer` bit 1 = Floor / bit 2 = Obstacle), and `CharacterMoveIntegrator` has a backstop that stops (instead of slides) on near-vertical normals. Guarded by `character_cast_filter_ignores_the_floor_it_rests_on`.

- [hits: 1] **All simulation-side physics state must live in ECS components; the `CollisionWorld` holds only immutable static geometry** — that's what keeps the double-buffered snapshots complete (bank-heist principle, Unity DOTS Physics "stateless" design). Character dims are the `CharacterBody` component (capsule origin = CENTER, matching scene authoring: halfLength = height/2 − radius, sample player 0.5/0.4); steering output is `MoveIntent`, zeroed at the top of every tick. Tick order: zero intents → plan clicks → schedule (path steering) → WASD `DirectMover` (after the schedule so it wins) → `CharacterMoveIntegrator` → publish.

## Test gotchas

- [hits: 1] **`TrySampleInterpolation` pins the snapshot pair it returns until the NEXT call — a test that samples once mid-run and then keeps calling `TickOnce` will exhaust the 32-world pool and the sim silently stops ticking (backpressure), capping movement.** The old `direct_move_input_slides_the_agent_and_clamps_to_the_navmesh` test only "passed" its ≤-edge assertion because of this freeze, not because of the clamp. In tests: sample right before asserting, or re-sample periodically so old pins release.

## Build / Toolchain

- [hits: 1] **Reference the sibling ParadiseEngine repo by its real relative path (`..\ParadiseEngine\src\...`) in `ParadiseGodot.sln`, NOT through the in-tree `ParadiseEngine` symlink.** Building engine projects through the symlinked path (`ParadiseGodotEditor/ParadiseEngine/...`) double-spells the same physical files, which breaks tooling that relies on canonical directory walking:
  - **`.editorconfig` discovery fails** → the engine's relaxed CA severities (e.g. `CA1062 = none`, `CA1716 = suggestion`) revert to SDK defaults and, with the engine's `TreatWarningsAsErrors=true`, become ~160 hard errors. Same `Paradise.ECS` builds with 0 errors via the real path, 78 via the symlink.
  - **NuGet restore races** on `obj/project.assets.json` ("file already exists") because the project is seen under two paths.
  The symlink is fine for IDE browsing only; the `.sln` and any `ProjectReference` must use `..\ParadiseEngine`.

- [hits: 2] **The Godot assembly's recursive `**/*.cs` glob sweeps EVERY sub-directory: any new sub-project at the repo root MUST get a `<Compile Remove="<dir>/**/*.cs" />` in `ParadiseGodot.csproj`.** First hit: the `ParadiseEngine` symlink flattened the whole engine into `ParadiseGodot.dll` (CS0106). Second hit (2026-07-06): adding `ParadiseRuntime`/`ParadiseRuntime.Tests` without exclusions made the glob compile their sources AND their `obj/` **generated `AssemblyInfo.cs`/`AssemblyAttributes.cs`** → CS0579 duplicate-attribute errors (misleadingly reported at `.godot/mono/temp/obj/Debug/*.AssemblyInfo.cs`, ParadiseGodot's own copy — the swept duplicates live in the sub-project's `obj/`). The top-level `DefaultItemExcludes` only covers the project's OWN `obj/`, never nested ones. Checklist when creating a sibling C# project: `dotnet sln add` + `Compile Remove` in ParadiseGodot.csproj, then `dotnet build ParadiseGodot.sln` to confirm.

- [hits: 1] **netstandard2.1 was dropped from the engine entirely (2026-07-01).** The 5 libs that used it — `Paradise.BLOB` (was netstandard2.1) and `Paradise.BT` / `BT.Nodes` / `BT.Builder` / `Rendering` (were `netstandard2.1;net10.0`) — are now **`net10.0` single-target**. The two **generators stay `netstandard2.0`** (hard Roslyn requirement; source generators run in the netstandard2.0 compiler). Consequences handled at the time: (a) BT's pack ItemGroup was `Condition="'$(TargetFramework)' == ''"` (the multi-target outer build) — under single-TFM that never fires, so it was made unconditional or README + the generator analyzer dll silently stop packing; (b) Rendering's netstandard2.1-only `System.Text.Json` PackageReference was removed (in-box on net10); (c) BT's `System.Runtime.CompilerServices.Unsafe` package became NU1510 (warning-as-error: "will not be pruned") and was removed; (d) dead `#if NET6_0_OR_GREATER` (ThrowHelper) and `#if NETSTANDARD2_1` (Rendering/Polyfills.cs — deleted) guards were stripped. **Resolved:** the Godot editor projects (`ParadiseGodot`, `ParadiseExport`, `ParadiseExport.Tests`) were also moved net8.0 → net10.0 (2026-07-01), so the whole repo is now net10 (except the two netstandard2.0 generators) and the editor CAN reference the engine libs. Godot.NET.Sdk 4.7.0 accepts net10 at build time; net10 runtime (10.0.4) is installed. Still worth confirming the Godot **editor** actually loads a net10 assembly at runtime (launch the editor) — build success alone doesn't prove hostfxr loads it.

- [hits: 1] **Bumping a lib from netstandard2.1 → net10.0 turns ON the default .NET analyzers** (CA-series), which only auto-enable for net5+ TFMs. With the engine's repo-wide `TreatWarningsAsErrors`, this surfaced new build errors in `Paradise.BLOB` (CA1822 make-static, CA2208 ArgumentException arg order) that never ran under netstandard2.1. Fix the code, don't disable analyzers. `Span<T>` is in-box on netstandard2.1 too, and LangVersion is 14.0 repo-wide (`src/Directory.Build.props`) independent of TFM.

- [hits: 1] **`Paradise.BLOB.Test` carried dead Unity remnants** that broke compilation: unguarded references to deleted port types `UnityStringBuilder` / `UnityBlobString` (in `TestBlobBuilder.cs` + a `TestUnityBlobString` class in `TestBlobDataTypes.cs`), plus `#if UNITY_BLOB`-guarded parity examples against `Unity.Entities` in `Examples.cs`. All removed (2026-07-01); every test kept its engine-side (`ValueBuilder`/`ArrayBuilder`/`StringBuilder<>`/`Ptr*Builder`) assertion. 625 tests pass; full `ParadiseGodot.sln` builds 0/0. Note: this lost the side-by-side Unity-vs-port parity scaffolding — re-add behind `UNITY_BLOB` only if byte-parity verification against Unity is ever needed again.

- [hits: 1] **The local-only `ParadiseEngine` symlink at the repo root is INSIDE `res://`, so the
  Godot editor scans the whole engine tree on startup** — once the engine's sample projects have
  build output, the scan spews `Unrecognized binary resource file: res://ParadiseEngine/src/
  Paradise.*.Sample/bin/...` errors and wastes time walking thousands of bin/obj files. Fix: an
  empty `.gdignore` at `~/proj/ParadiseEngine/.gdignore` (Godot skips any directory containing
  one). The symlink is gitignored in the game repo and the `.gdignore` lives in the engine repo
  — if it goes missing (fresh engine clone), the error spam comes back. Also: a rename/deletion
  of a C# project leaves stale `<old-name>/obj` NuGet leftovers that survive `git rm` — delete
  the directory itself, not just tracked files.

## Engine: Slang shader bootstrap (macOS)

- [hits: 1] **macOS Slang release tarballs cannot be extracted by .NET's managed `System.Formats.Tar`.** They are packed by Apple `bsdtar` and carry PAX extended-header records for extended attributes (e.g. `LIBARCHIVE.xattr.com.apple.cs.CodeSignature`) whose values are raw binary. `TarReader` throws `InvalidDataException: The extended header contains invalid records` and the process aborts (SIGABRT / exit 134) — which looks like a "download failure" but the download is byte-perfect (SHA256 matches). Fix in `ParadiseEngine/tools/slang/SlangBootstrap.cs`: extract `.tar.gz` by shelling out to the platform `tar` (libarchive/GNU tar) instead of `TarFile.ExtractToDirectoryAsync`. `tar.gz` is never the Windows archive format here (Windows uses `.zip`).

## Godot GLTF export (MeshGlbExporter)

- [hits: 1] **`GltfDocument.AppendFromScene` exports only OWNED descendants (the same rule as
  `PackedScene.Pack`)** — a `Node.Duplicate()` clone keeps children but their `Owner` points at
  the original scene root, so the exported GLB silently contains ONLY the root node (272-byte
  files, zero meshes, no error). After duplicating a subtree for export, re-own every
  descendant (`child.Owner = cloneRoot`, recursively) before `AppendFromScene`.

- [hits: 2] **Procedural textures (GradientTexture2D etc.) export differently in GUI vs headless
  editors.** Material JSON never references them (`MaterialExporter.TexturePath` needs a
  `ResourcePath`). GLB baking depends on the renderer: a HEADLESS editor exports textureless
  GLBs (no GPU to rasterize the gradient), but the GUI editor bakes the rendered image into the
  GLB as embedded PNG — which then makes the KTX2 encode pass MANDATORY and rewrites content-key
  fixtures with textured variants. Consequences: (a) `data/` fixtures must be regenerated
  headless to stay stable; (b) a GUI scene save (auto-export hook) fails with ToolMissing unless
  the `ktx` CLI is installed (`PARADISE_KTX_PATH` / vendored `third_party/tools/KTX-Software` — a
  GUI-launched editor does not inherit the shell PATH); (c) editor-side launch actions must not
  export as a side effect (the Play .NET button deliberately only consumes existing data/).
